# Webhook 出站集成

## R 原文依据

- [/guides/webhooks](https://docs.useplunk.com/guides/webhooks)："Plunk automatically tracks a set of internal events that you can use as workflow triggers. These events cannot be manually tracked via the API — they are generated by the system."
- [/guides/webhooks](https://docs.useplunk.com/guides/webhooks)："**Body** (optional): Custom request body. When omitted, Plunk sends the default payload shown below. When provided, the value replaces the default payload entirely and is JSON-encoded before being sent."
- [/guides/webhooks](https://docs.useplunk.com/guides/webhooks)："`{{id}}`, `{{email}}` — The contact's ID and email... `{{<key>}}` (top-level) — Any key from the contact's `data` JSON... `{{event.<key>}}` — Webhook-only. Fields from the trigger event payload."
- [/guides/webhooks](https://docs.useplunk.com/guides/webhooks)："The HTTP `method` is **not** templated — it must be a literal verb... The `url` must include a static scheme (`http://` or `https://`); placeholders are supported inside the URL but cannot replace the scheme."
- [/guides/webhooks](https://docs.useplunk.com/guides/webhooks)："**Timeout**: each request times out after **10 seconds**. Long-running endpoints should accept the request, queue the work, and return `2xx` quickly."
- [/guides/webhooks](https://docs.useplunk.com/guides/webhooks)："**Redirects**: up to 5 redirects are followed. Each hop is re-validated against the SSRF rules... **Public URL required**: your webhook endpoint must be reachable on the public internet. Webhooks pointed at private or internal addresses (loopback, RFC 1918 ranges, etc.) won't be delivered."
- [/guides/webhooks](https://docs.useplunk.com/guides/webhooks)："**No automatic retries**: a non-2xx response or timeout fails the workflow step. Build idempotency into your handler and use workflow logic (a `WAIT_FOR_EVENT` step, a fallback branch) if you need retry semantics."
- [/guides/webhooks](https://docs.useplunk.com/guides/webhooks)："All email events include an `emailId` field that matches the Plunk email record ID returned when you send an email via `POST /v1/send`... This eliminates the need to match by contact email + timestamp."

## I 解释

Plunk 没有独立的"webhook 配置"页面——出站 webhook 就是 workflow 里的一个步骤。这个设计决定了两件事：能监听什么完全取决于有什么事件，能加什么逻辑完全取决于 workflow 的图能力（CONDITION 过滤、DELAY 缓冲、UPDATE_CONTACT 打标都可以排在 WEBHOOK 之前）。所以它更像"事件路由"而不是"回调订阅"。

事件分成两大类。系统内部事件由 Plunk 自己产生（email.* 七种、contact.subscribed/unsubscribed、segment.<slug>.entry/exit），**不可通过 `/v1/track` 手工上报**——这是保留事件名，硬 track 会被拒。自定义事件则是你自己 track 的，载荷原样带过来。

payload 有两种模式，而且是非此即彼：不填 body 就发默认四段结构 `{ contact, workflow, execution, event }`；一旦填了 body，就**整体替换**，四段结构一个都拿不到。选默认还是自定义，本质是"要开箱字段（尤其 `emailId`）还是要对接方要求的固定格式"。

变量作用域是 SEND_EMAIL 模板作用域的超集：`{{id}}` / `{{email}}`、contact `data` 的顶层键与 `{{data.<key>}}`、执行 context 的键、三个订阅管理 URL，外加 webhook 独有的 `{{event.<key>}}`。可插值的位置只有三处：url、header 的值、body。method 不参与模板化，url 的 scheme 必须静态——这两条是 SSRF 防护的一部分。

交付侧的约束构成了一张很紧的网：10 秒超时、最多 5 跳重定向且每跳重新过 SSRF 校验、必须公网可达（loopback 与 RFC 1918 不投递）、只接受 http/https。最关键的是**没有自动重试**——非 2xx 或超时直接把这一步判失败。所以可靠性的责任几乎全在接收端：接住、入队、立刻返 2xx，handler 自己做幂等，需要重试语义就用 WAIT_FOR_EVENT 或兜底分支在 workflow 里搭。

鉴权建议用共享密钥 header 而不是 IP 白名单，理由是出口 IP 会变。

## A1 示例

**示例 1 · 默认 payload 与可用变量**（来自 `/guides/webhooks`）

- 输入/问题：不配 body 时到底能收到什么，能往请求里插哪些变量。
- 怎么执行：省略 body 字段，Plunk 发送 `{contact:{email,subscribed,data:{name,plan}}, workflow:{id,name}, execution:{id,startedAt}, event:{subject,from,fromName,messageId,emailId,templateId,campaignId,sourceType,bounceType,bouncedAt}}`。URL 可写成 `https://api.example.com/users/{{id}}/events`，headers 写 `{"Authorization":"Bearer your-secret-token"}`，body 若自定义可写 `{"email":"{{email}}","plan":"{{plan}}","referrer":"{{event.referrer}}"}`，method 只能写字面的 `POST`。
- 产出/预期输出：文档未说明（原书未给出执行结果）；可判定的是 method 不可插值、url 的 scheme 不能被占位符替换。

**示例 2 · 用 emailId 对齐发送请求**（来自 `/guides/webhooks`）

- 输入/问题：收到 `email.open` / `email.bounce` 后，怎么知道它对应我哪次发送。
- 怎么执行：`POST /v1/send` 的响应里取 `data.emails[].email`（如 `ac32f08e-c6b9-45d3-9824-a73dff1e3bbf`）→ 存进自己的库 → webhook 到达时按 `event.emailId` 匹配。
- 产出/预期输出：文档未说明（原书未给出执行结果）；文档明说的收益是不必再按"邮箱 + 时间戳"模糊匹配，也不必为拿 provider `messageId` 而额外监听 `email.sent`。注意：409 重试拿不回这个 ID，必须在首次成功时就落库。

**示例 3 · 退信/投诉监控：条件 + 延迟 + 打标再转发**（来自 `/guides/webhooks`）

- 输入/问题：只想把硬退信同步到自己的系统，且要合并批量、带标记。
- 怎么执行：workflow 触发器用 `email.bounce` 或 `email.complaint`；在 WEBHOOK 前排 CONDITION（只放行 `bounceType` 为硬退信的）、DELAY（短延迟以批量合并相关事件）、UPDATE_CONTACT（先打标再外发）。
- 产出/预期输出：文档未说明（原书未给出执行结果）。

**示例 4 · 慢处理导致事件永久丢失**（来自 `/guides/webhooks`，反例）

- 输入/问题：handler 里同步写库、调第三方、生成 PDF，耗时超过 10 秒。
- 怎么执行：超时即判该步骤失败，且没有自动重试。
- 产出/预期输出：事件永久丢失、下游数据不一致；正确做法是"接住 → 入队 → 立刻返 2xx"，并在 handler 内做幂等，需要重试语义时用 workflow 的 `WAIT_FOR_EVENT` 步骤或 fallback 分支自建。

## A2 何时会用

**用户场景**

1. 邮件退信、投诉要实时同步到自己的数据库或告警通道。
2. 想把自定义事件（下单、注册）一次上报后分发到多个外部系统。
3. 收到 webhook 后要把事件和自己的发送请求对上号。
4. 接收端偶发超时或返回非 2xx，事件再也回不来。
5. 本地联调时把 webhook 指向 localhost / 内网地址，请求根本发不出去；或想只转发满足特定条件的事件（只报硬退信、只通知特定套餐的联系人）。

**语言信号**

`webhook` / `outbound webhook` / `回调` / `推送` / `WEBHOOK step` / `payload` / `default payload` / `emailId` / `event.emailId` / `10 秒超时` / `timeout` / `无重试` / `no automatic retries` / `SSRF` / `redirect` / `公网可达` / `public URL` / `idempotency` / `幂等` / `shared secret` / `internal events` / `email.bounce` / `email.complaint`

**与相邻能力的区分**

- 本卡负责 WEBHOOK 步骤的出站契约：payload 结构、变量作用域与插值边界、超时/重定向/SSRF、重试语义、接收端设计。
- `plunk-workflows` 负责 workflow 图本身（trigger、step、branch、splice、执行状态机）——本卡只把 WEBHOOK 当作其中一个节点来配。
- `plunk-tracking-events` 负责自定义事件怎么上报、哪些事件名被保留——本卡只消费事件，并明确系统事件不可手工 track。
- `plunk-inbound-email` 负责 `email.received` 的入站链路与 verdict 字段——本卡只在转发入站邮件时与它交接。
- `plunk-sending-health` 负责退信/投诉的列表卫生含义（`Permanent` 计入退信率、`Transient` 不计）——本卡只讲怎么把事件转发出来。
- `plunk-transactional-send` 负责 `/v1/send` 的请求与响应——本卡只借用响应里的 `emailId` 做关联键。

## E 执行步骤

**输入契约（必需信息）**

1. 要监听的事件名（系统内部事件之一，或你自己的自定义事件名）。
2. 接收端 URL（必须公网可达）+ 期望的 method + 是否需要自定义 body。
3. 鉴权方式（共享密钥 header）+ 是否有条件/延迟/打标等前置步骤。
4. 缺失时先问：① 接收端能否在 10 秒内返回 2xx；② 是否需要默认 payload 里的 `emailId` 做关联（决定了要不要自定义 body）；③ 事件名是否属于不可手工 track 的系统事件。

**步骤**

1. **确认事件源类型**：系统事件只能用下面这些，且它们**不能**通过 `/v1/track` 手工上报（它们是系统生成的，硬 track 会被保留事件名校验拒绝）——

   | 类别 | 事件 |
   | --- | --- |
   | 邮件 | `email.sent`、`email.delivery`、`email.open`（首次打开）、`email.click`（首次点击）、`email.bounce`、`email.complaint`、`email.received`（需入站配置） |
   | 联系人 | `contact.subscribed`、`contact.unsubscribed` |
   | 分群 | `segment.<slug>.entry`、`segment.<slug>.exit` |
   | 自定义 | 你自己经 `/v1/track` 上报的事件，名字不要撞上 `email.*` / `contact.*` / `segment.*` |

   `contact.subscribed` / `contact.unsubscribed` 默认 `event` 为空对象 `{}`；仅当退订由 bounce / complaint 自动触发时带 `{ reason: "bounce" \| "complaint" }`。完成标准：事件名已确认属于可监听集合。注意文档在本页写 `segment.<name>`、其他页写 `segment.<slug>`，实际取段名的 slug 版本（如 "VIP Users" → `segment.vip-users.entry`）。
2. **建 workflow 并选 trigger**：在 dashboard 的 Workflows 里新建，把上一步的事件设为触发事件（如 `email.bounce`）。完成标准：workflow 已存在，trigger 事件名正确。
3. **加 WEBHOOK 步骤并配四项**：URL（公网可达，含静态 scheme）、Method（默认 `POST`，推荐）、Headers（可选，JSON，用于放 `Authorization: Bearer <secret>`）、Body（可选）。完成标准：四项配置齐且 URL 是 `https://` 开头的公网地址。
4. **决定 body 走默认还是自定义**：不填 body → 发送默认 payload `{contact:{email,subscribed,data}, workflow:{id,name}, execution:{id,startedAt}, event:{...}}`，含可用于关联的 `emailId`；填了 body → **整体替换**默认 payload，四段结构一个都拿不到，需要的字段必须自己写全。所有邮件类事件共享八个基础字段：

   | 字段 | 说明 |
   | --- | --- |
   | `subject` | 邮件主题 |
   | `from` / `fromName` | 发件地址与显示名 |
   | `messageId` | 服务商侧消息 ID（用于与投递日志对齐） |
   | `emailId` | Plunk 邮件记录 ID，与 `POST /v1/send` 返回的一致 |
   | `templateId` / `campaignId` | 模板 / 活动 ID，不适用时为 `null` |
   | `sourceType` | `TRANSACTIONAL` / `CAMPAIGN` / `WORKFLOW` / `INBOUND` |

   各事件再叠加专属字段（`sentAt` / `deliveredAt` / `openedAt`+`opens`+`isFirstOpen` / `link`+`clickedAt`+`clicks`+`isFirstClick` / `bounceType`+`bouncedAt` 或 `transientBounce` / `complainedAt` / 入站那一套）。完成标准：明确写下选择理由；若下游需要 `emailId` 做关联而选了自定义 body，必须在 body 里显式带上 `"emailId": "{{event.emailId}}"`。
5. **插变量（可选）**：可插值位置只有 url、header 的值、body 三处，作用域是 SEND_EMAIL 模板作用域加一个 webhook 专属命名空间——

   | 变量 | 取值 |
   | --- | --- |
   | `{{id}}` / `{{email}}` | 联系人 ID 与邮箱 |
   | `{{<key>}}`（顶层） | 联系人 `data` JSON 里的任意键（如 `{{firstName}}`、`{{plan}}`） |
   | `{{data.<key>}}` | 同一份联系人数据，经 `data` 命名空间寻址 |
   | `{{event.<key>}}` | **webhook 专属**：触发事件载荷字段（如 `{{event.subject}}`） |
   | `{{<key>}}`（context） | MANUAL 执行启动 execution 时传入的 context 键 |
   | `{{unsubscribeUrl}}` / `{{subscribeUrl}}` / `{{manageUrl}}` | 每联系人订阅管理 URL |

   完成标准：插值位置合法——method 必须是字面动词（不参与模板化），url 的 scheme 必须是静态字面量（占位符不能替换 scheme）。
6. **按需要排前置步骤**：CONDITION（只放行特定子集，如只报硬退信）、DELAY（短延迟做批量合并）、UPDATE_CONTACT（先打标再外发）。完成标准：webhook 只在预期条件下发出。
7. **启用 workflow**：配完后 `enabled` 打开——workflow 创建时默认是 `false`，不开不会有任何请求。完成标准：触发一次事件后接收端收到请求。
8. **设计接收端（六条硬约束）**：① 公网可达且用 HTTPS；② 收下请求 → 入队 → 立刻返 2xx（10 秒内）；③ 校验共享密钥 header 而不是 IP 白名单（出口 IP 会变）；④ handler 内做幂等；⑤ 需要重试语义时在 workflow 里自建（`WAIT_FOR_EVENT` 步骤或 fallback 分支）；⑥ 不要用短链/网关跳转链，直接给最终地址。完成标准：一次人为的重复投递不产生重复副作用；一次慢处理不丢事件。
9. **用 emailId 对齐发送**：发信时把 `POST /v1/send` 响应里的 `data.emails[].email` 落库，webhook 到达时按 `event.emailId` 匹配。完成标准：`email.open` / `email.bounce` 能直接定位到业务发送记录；不要按"邮箱 + 时间戳"猜，也不要为拿 `messageId` 而专门监听 `email.sent`。
10. **⚠️ 重试语义按"无自动重试"做防御**：文档在这一处写 "No automatic retries: a non-2xx response or timeout fails the workflow step"，但在 `/concepts/workflows` 的 FAILED 描述里又写 "webhook returned non-2xx after retries"。⚠️ 文档口径不一致，两者并列，不要替文档做取舍。工程上按无重试设计：幂等做在自己的 handler，重试语义用 WAIT_FOR_EVENT / 回退分支自建。完成标准：接收端在"只投递一次"的前提下仍然正确。
11. **排障顺序**：请求没到达 → ① 确认 workflow `enabled` 为 true；② URL 是否公网可达（loopback、RFC 1918、容器内网都不投递）；③ 是否有超过 5 跳的重定向链，或中间跳到了内网地址（每跳都重新过 SSRF 校验）；④ 单次请求是否超过 10 秒。完成标准：定位到四处之一；被判失败的步骤不会自动重投。

**输出契约**

- 产出：一个已启用的、带 WEBHOOK 步骤的 workflow + 一个满足六条硬约束的接收端点 +（按需）emailId 关联方案。
- 验收：① 触发一次目标事件，接收端在 10 秒内收到并返回 2xx；② 默认/自定义 payload 与预期一致（自定义时 `emailId` 已显式带上）；③ 共享密钥校验通过；④ 重复投递一次不产生重复副作用；⑤ 若监听 `email.*`，webhook 里的 `event.emailId` 能对上 `/v1/send` 的响应。
- 交付后必须交代的三件事：① 没有自动重试（文档另一处暗示有，两者并列），幂等做在你自己的 handler；② 10 秒超时意味着慢活必须入队；③ 自定义 body 会丢掉默认四段结构。

## B 边界与失效

1. **⚠️ 重试语义两处矛盾（`p154`）**：`/guides/webhooks` 说无自动重试，`/concepts/workflows` 的 FAILED 成因又说"webhook 重试后仍非 2xx"。两者并列，不要替文档做取舍；设计时按无重试做防御。
2. **不要把 webhook 当可靠的投递保证**：10 秒超时 + 非 2xx 即失败 + 无自动重试，任一环节出问题事件就永久丢失。需要可靠投递就得自己在 workflow 里搭重试，且接收端必须幂等。
3. **不要指向内网/本地地址做联调**：loopback 与 RFC 1918 网段不投递，这是 SSRF 规则的一部分；本地开发要用公网可达的调试端点（文档示例用 webhook.site）。
4. **不要依赖重定向链**：最多跟随 5 跳，且**每一跳**都重新过 SSRF 校验，跳到内网即失败。直接给最终地址。
5. **不要以为填了 body 还能拿到默认字段**：body 一旦提供就整体替换 `{contact, workflow, execution, event}`，联调时最容易表现为"emailId 不见了"。
6. **不要手工 track 系统事件**：`email.*`、`contact.*`、`segment.*` 由系统产生，用 `/v1/track` 上报会被保留事件名校验拒绝；它们是触发器，不是可上报数据。
7. **不要把 method 或 url 的 scheme 写成变量**：method 必须是字面动词，url 的 scheme 必须静态——这两处不参与模板化。
8. **不要用 IP 白名单做鉴权**：出口 IP 会变；用共享密钥 header，并像其他共享密钥一样定期轮换。
9. **不要在 handler 里做同步重活**：写库、调第三方、生成 PDF 这类操作应入队后异步执行，handler 只负责接住并尽快返 2xx。
10. **不要指望 webhook 步骤替你做过滤或批量**：它是 workflow 的一个节点，过滤要前置 CONDITION、合批要前置 DELAY；把判断逻辑放到接收端再"扔掉"等于白跑一次投递并占用执行。
11. **不要用 `email.open` / `email.click` 的到达次数当真实次数**：这两个事件是"首次"语义（载荷里另有 `opens` / `clicks` 总数与 `isFirstOpen` / `isFirstClick`），且追踪本身存在系统性假阳性，见 `plunk-tracking-events`。
12. **高危/不可逆提醒**：webhook 步骤的失败会直接把所属 execution 推到 FAILED，且不会重投；对外系统而言这是一次性的副作用触发点（如创建工单、扣减库存），因此接收端不做幂等就可能重复建单——这类下游副作用无法在 Plunk 侧撤销。
